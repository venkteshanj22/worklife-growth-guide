# CareerOS Phase 2 — Candidate Master

## Delivered
- All Candidates, Active Candidates, Add Candidate, Edit Candidate, Candidate 360° Overview and Activity.
- Multi-record education/employment; career gap, career profile, program details, staff assignments and optional photo.
- Search by ID/name/mobile/email; status, plan, employment, consultant, enrollment range and portal filters; sorting and bounded pagination.
- Future candidate tabs and future menu entries remain Coming Soon. No Phase 3 modules were built.

## Database and permissions
New tables: candidates, candidate_education, candidate_employment, candidate_status_history, candidate_assignments, candidate_assignment_history, candidate_portal_links, candidate_activity, candidate_program_plans, candidate_year_counters.
No Phase 1 table definitions were changed. Existing permissions and role_permissions received Candidate permission rows/default grants; significant actions append to existing audit_logs.
Added candidates.create, candidates.edit, candidates.status, candidates.assign, candidates.portal, candidates.view_all and candidates.view_assigned; retained candidates.view. Requested role defaults are applied and visible in the existing matrix.

## Integrity and security
- Candidate IDs generated by a database trigger using an atomic per-year counter; C361-YYYY-0001, read-only, unique. Creation year uses Asia/Kolkata.
- All thirteen specified journey statuses; new records Draft or Enrolled; status changes retained with actor/time/remarks.
- Assignment changes require active matching-role staff, retain previous/new user history, and never erase relationships when a staff account becomes inactive.
- Optional portal link is unique on both candidate and user. Existing Candidate-role account linking, disabling/reactivation and new email invitations are implemented. Invitation failure preserves the business record.
- Candidate mutation RPCs verify caller permissions and record scope in the database. Child reads use the same row scope; no public candidate access and no browser write policies.
- Assigned-only staff see their applicable assignments only. Candidate Home uses an explicit four-field summary, excluding internal notes/history/activity.
- Candidate save/history/activity/global audit use database transactions.

## Assumptions and limitations
- Verification candidates are explicitly named Phase 2 Verification and marked Cancelled after checks, rather than presented as real candidates or included in active counts. The existing test Candidate account remains linked to its labelled verification candidate.
- Program plans are data-configurable; no separate plan-management page was requested.
- Optional photos are private inline image data, capped at 1 MB; migrate to private file storage if larger volumes require it.
- Candidate Activity currently shows the latest 200 events; older events remain stored. Dedicated history paging is a future enhancement.
- Existing-account portal linking was verified. Real invitation delivery and recovery-link behavior require a deliverable recipient and a published site; they were not verified against a real inbox.
- Historical users who are inactive remain referenced; some internal system/history fields display UUIDs when their names are unavailable in active choices.
- Database counter concurrency was tested; annual rollover and inactive-staff assignment behavior were enforced in code but not simulated against modified account status/year.
- No additional credentials or configuration are required for existing-account linking. Publishing was not requested.
